# Build procedure — end to end

Follow after Step 0 (orientation + prompting-level gate) in `SKILL.md`. Scale the
verbosity of every **[needs you]** prompt to the level the user picked. Read
`references/style-guide.md` first — it is the single reference for the templates'
mechanics (field contract, Explore view, feeder recipe, `.trex`, hosting). This
file is the flow and cross-references it rather than restating it. All tools are
your own in-Studio tools. For the "why" behind the guardrails below, see
**Known failure modes** at the end.

**Delivery mode** (chosen in Step 0):
- Steps 0b–4 are shared.
- **Packaged** (the default): after step 4, go to **4P**, then finish with
  Cleanup. Skip steps 5–7, because there is no feeder sheet, host, dashboard or
  Publish dialog.
- **Hosted**: continue with steps 5–7.

## 0b. Check for prior progress on this story first — automatic

Before connecting anything, check this skill's memory index and
`.build/scrollytelling-demo-builder/` scratch dir for an in-progress or
completed run on the same story/workbook (e.g. a prior session's notes naming

## 1. Connect the published datasource — [needs you]

The datasource question is pinned in `SKILL.md` Step 0 item 7 and was already
asked; do not ask it again or ask the audience here.

Connecting/authorizing is their action (sign-in, credential, or selecting it in
Studio). Confirm you can query it
before proceeding. Your read/query path is `mcp__tableau-web__query-datasource`
(VizQL Data Service) — it is query-only; it cannot publish or write.

In **packaged** mode the Studio workbook is only your authoring and probing
scratchpad. The published `.twbx` is generated by `package_extension.py`. Still
save once, so there is a record of what you probed.

**Once connected, save immediately** with an explicit `filePath` (e.g.
`~/Desktop/<workbook-name>.twbx`) — before any dashboard or extension work. This
is a known-good checkpoint: dashboard corruption (see *Known failure modes §A*)
can force recovery by closing without saving and reopening the last good file,
which only works if a good save exists. Save again after `feed_data` is built
(step 5, before any manual dashboard step), and encourage the user to save after
each manual dashboard action (floating `feed_data`, then adding the Extension)
rather than doing all of it before the first save — that isolates which single
action triggers corruption if it recurs, instead of losing the whole dashboard.

## 2. Examine the data & find the signal — automatic, may [needs you]

- Read the datasource's metadata (fields, types, captions) via VizQL, then run
  aggregate probes to surface candidate signals: a trend over time, a divergence
  (one metric up while a related one falls), a concentration (a few members drive
  most of a total), an anomaly, or a threshold breach.
- **Batch probes to minimize `query-datasource` calls.** Where the tool supports
  multiple measures/dimensions in one query, pull them together (e.g. all
  candidate measures at the same date grain in one call) rather than issuing a
  separate call per candidate signal — each call has real latency, especially on
  a live (non-extract) connection. **Early-exit:** once a probe surfaces a clear,
  strongly-evidenced signal, stop probing further candidate angles — don't run
  every possible aggregate combination just to be thorough if the first one or
  two already tell a clean story.
- **Scale the probe to the datasource's width/depth (locked).**
  - Narrow (under 10 fields): probe all numeric measures in one call.
  - Typical (10 to 50 fields): probe every numeric measure in batches of at most 10
    per call, so "N of N" in the proposal stays the full count.
  - Wide (50 to 100 fields): probe the numeric measures only (dimensions are not
    probed for the signal), at most 10 per call, and cap the probe at the first 20
    numeric measures A to Z when there are more. Say "20 of N probed" in the
    Measures line and name the cap as a default the user can override.
  - Very wide (over 100 fields): ask the user for the measure subset (up to 10)
    before probing; do not pull every field.
  - Tiny (under 28 periods at the finest grain, the minimum for a 14-period
    baseline plus a 14-period comparison): skip the move-start and yearly steps,
    use the full history, and say there isn't enough history to sub-window.
  - Under 400 rows or over 1,000,000 rows: no change to the rules. For large row
    counts use aggregate calls only (grouped and summarized); only the `feed_data`
    feeder (step 5) needs row-level granularity.
- **If `query-datasource` returns empty rows or errors** (bad field reference,
  RLS blocking all rows, connection timeout), don't guess a signal from
  metadata alone — retry with a narrower field/date scope once; if it still
  fails, [needs you]: report the exact error and ask whether to pick a
  different datasource or field scope.
- **Ground every claim in rows you actually queried.** Never invent a signal.
- Form 1–2 candidate story angles with the numbers that support them. If more than
  one is compelling, or the "so what" is ambiguous, [needs you]: present the
  angles with their evidence and let the user choose. Otherwise state the angle you
  found and proceed (respecting the prompting level — Minimal may skip confirming).
- **Measures, nulls and grain (check before trusting a signal).**
  - **Null rate:** for each measure behind a candidate signal, compare the
    count of non-null values to the row count. If more than 10% are null, flag it
    to the user. Averages skip nulls, so a KPI can look healthy while hiding
    missing data. Do not build a headline number on a measure above 50% null.
  - **Aggregation by measure type (locked):**
    - Totals (volumes, counts, dollar amounts): `SUM`.
    - Percentages, hours and indexes: `AVG`.
    - Per-unit ratios (for example revenue per load, cost to serve, labor hours
      per load): when the numerator and denominator are both in the datasource,
      compute the sum of the numerator divided by the sum of the denominator.
      Otherwise use `AVG` and label it "average" on the page.
    - Never sum a distinct count across days or groups; query it at the grain you
      show, or drop that KPI.
    - Use the same rule for the probe, the story and the live query, and name
      the rule used for each measure in the proposal.
  - **One grain per chart:** do not combine measures queried at different date
    grains in the same chart or KPI. Re-query both at the shown grain.
  - **Window edges:** dates arrive as ISO strings. Check that the first and last
    day of the chosen window match your probe, since a time-zone shift can move
    a day across the boundary. Compare against the probe, not the page.
- **Locked signal thresholds (defaults; the user can override any of them, and
  you must name the defaults you used).** Compute each from the probe rows:
  - **Trend:** a measure trends if its last-period value differs from its
    first-period value by more than 10% (relative), in one direction, with no
    more than one direction reversal across the window.
  - **Divergence:** two measures diverge if one rises more than 5% while the
    other falls more than 5% over the same window. Test every pair of numeric
    measures (a pair counts as related when both are in the same datasource) and
    list each pair that diverges, with both changes.
  - **Percent and rate fields** (such as Discount) use the field's per-period
    AVG as the datasource returns it, then the plain mean of those per-period
    values across the block; never weight by row counts.
  - **Measures probed:** count every numeric measure the datasource lists,
    plus a Profit Ratio whenever the datasource has both a Profit and a Sales
    measure, even if it lists none (a probe measure, not a new datasource
    field; say so in its Rule column). Include calculated ratio measures (computed as the sum of the numerator over
    the sum of the denominator over the whole 14-period block; never the average
    of per-period ratios, which blows up when a period's denominator is near zero
    and gives a different answer each run). The proposal table's columns are
    Measure, Rule, First 14 vs last 14, and (only when step 3b ran) First vs last
    full year, then Verdict. State "N of N" from that list, followed by the names
    in parentheses, and name measures by their field names (Quantity, not "units
    sold"). The yearly comparison covers every measure, ratios included, each
    computed as in the first-14 comparison. Do not add
    measures of your own, such as row counts, to the count.
  - **Concentration:** the top 3 members hold more than 50% of the total.
  - **Anomaly:** a point more than 3 standard deviations from the window mean.
  - **Not a signal:** anything under these thresholds is noise. Do not build a
    story on it; say so with the numbers and ask for a different angle or
    datasource.
  - **Qualification is mechanical, never by judgment.** For every numeric measure,
    compute the relative change between the average of the first 14 periods and the
    average of the last 14 periods at the finest grain. Over the locked threshold
    means it qualifies, even if its shape is gradual or stepped; under means noise.
    Compute the 3 SD move start numerically, never by eye. In the proposal, list
    every measure with its change and its aggregation rule, and say "qualifies" or
    "noise" for each.
  - **Minimum window:** at least 14 days (or 14 periods at the chosen grain). With
    less, use the full history and say there isn't enough to sub-window.
- **Tie-breaking default when angles are equally compelling and the user hasn't
  weighed in:** prefer a trend or divergence signal over a pure concentration
  signal — a change over time reads as a clearer "so what" for a scrolly format
  than a static "these 3 members dominate" snapshot. Only apply this default
  when truly tied; if one angle has materially stronger evidence, use that one
  regardless of type.
- **Determine the time window the story should show — don't default to the
  full history.** A trend/divergence/anomaly signal usually reads clearly over
  some sub-range and gets diluted or hidden by noise/flat periods outside it
  (this showed up as: a line chart plotting the entire date range instead of
  the window that actually tells the story). Probe a few candidate windows
  (e.g. last 30/60/90 days, or the range bounding the anomaly/inflection you
  found) with aggregate queries and pick the one with the best signal-to-noise
  for the chosen angle — the shortest window that still shows the trend
  clearly, not the longest window available.
- **Locked window rule (follow this procedure exactly, do not eyeball):**
  0. Grain: use the datasource's finest native date grain for every period
     count and window edge (daily rows mean daily periods). Never roll up to
     weeks or months to compute the window. Probe every numeric measure in the
     datasource (not a subset) at the finest grain, batching measures per call,
     before ranking signals. Rank by relative change against the locked
     thresholds. Never describe a measure as flat or noise unless you queried it.
  1. Lead signal: the qualifying signal with the largest relative change. Ties
     break in this order: divergence, trend, concentration, anomaly. Other
     qualifying signals become supporting chapters.
  2. Move start (compute it numerically, never by eye). Baseline: the mean and
     standard deviation of the lead measure over the first 14 periods. Move
     start: the first period from which the 7-period trailing average of the lead
     measure stays more than 3 baseline standard deviations away from the
     baseline mean, in the direction of the move, through the latest period. If
     no period qualifies there is no move start (a steady climb with seasonal
     spikes often has none): say so with the numbers and go to step 3b.
  3. Window start: 14 periods before the move start. Window end: the latest
     complete period (mark a partial final period as partial).
  3b. No move start: the window is the full history. Say it is a steady change
     with no step, and note that comparing the first 14 and last 14 periods can be
     partly seasonal. The window is still confirmed with the user.
     Yearly comparison (only here): for EVERY measure, compare its value per
     period in the first full calendar year with the last full calendar year:
     the year's total divided by the number of periods that have rows in that
     year, never the raw year total, because the first and last years can have
     different numbers of periods (ratios as sum over sum within each year), using the same thresholds. A year
     is full when the data has rows in both its first and its last month; judge
     this from the data only, never from today's date (a year that runs past today
     still counts, and the proposal flags that in the caveats). When
     this step ran, the yearly comparison decides the verdict, because first-14
     vs last-14 is partly seasonal; the first-14 column is shown for reference
     only. A measure that qualifies on the yearly comparison is "qualifies" even
     if first-14 shows noise; one that qualifies only on first-14 is "noise". The
     lead signal, any divergence and the chapters are chosen from the yearly
     results, before the proposal, so the proposal and the build tell the same
     story. Rank measures by absolute yearly change, largest first: that order
     sets the lead signal, the table rows and the chapter order.
  4. Never widen the window past 3 times the length of that move. If the full
     history is shorter than 14 periods, use it and say so.
  5. If no signal meets the locked thresholds over this window, treat it as
     not a signal.
- **[needs you]: always present the window you determined and ask for
  confirmation before building on it** — even at Minimal prompting (this is a
  hard ambiguity point, like the story-angle choice above, not a skippable
  nice-to-have). State the window and the evidence for it (e.g. "last 60 days —
  the metric is flat before that, so the full history would bury the shift"),
  then ask: use this window, or a different one? If the user names a different
  window, use theirs instead and re-check the signal still holds over it before
  proceeding — a window picked without checking the signal can bury the story
  just as easily as skipping this step entirely.
- **If the user rejects the angle or window:** re-probe once with their
  stated preference (angle, or window), re-check the signal holds, and present
  the result for confirmation. If it does not hold, say so plainly with the
  numbers and offer the next-best angle; never build on a signal the rows do
  not support.
- **Carry that window forward as a hard constraint on the feeder sheet** (step
  5) — a `Day_Offset`-in-range filter (or equivalent date filter) on
  `feed_data`, not just on `cols`/probe queries. If the extension's date axis
  ends up showing rows outside the chosen window, that's a bug in `feed_data`'s
  filter, not a chart-config issue on the HTML side.

## 3. Draft the story & pick the scrolly design — may [needs you]

- **[needs you] if not already clear from the ask: who is this for?** An exec/
  CFO one-pager (short, few chapters, one headline number per beat) reads and
  builds very differently from an analyst deep-dive (more chapters, more
  supporting detail/segments). Audience also affects template choice — a
  pinned/sticky single-visual pattern suits a tight exec brief; a numbered-
  chapter linear narrative suits a longer analyst walkthrough. Don't guess
  this silently if it's ambiguous.
- Choose the template pattern that fits the signal (`style-guide.md`): numbered
  chapters (`coo-brief.html`) for a linear narrative, or pinned/sticky
  (`cfo-brief.html`) for a single evolving visual. State which and why.
  **Locked tie-break when audience/signal don't clearly favor one:** if the
  draft has 4+ distinct narrative beats, default to numbered-chapter
  (`coo-brief.html`); if 3 or fewer beats built around one evolving
  visual/metric, default to pinned/sticky (`cfo-brief.html`). Only override
  this default when the audience explicitly calls for the other (e.g. a
  4-beat exec one-pager may still prefer pinned/sticky for brevity — say so).
- **Non-time-series signal (a concentration/anomaly with no clean date axis):**
  the template's chapter shape still applies, but swap the date-driven charts
  (trend lines, day-window KPIs) for the analogous rank/breakdown chart the
  template already has for a segment/dimension (e.g. the facility rail or
  segment quadrant) rather than forcing a trend chapter over flat data. Skip
  the time-window steps below for this case — there is no window to pick.
- Draft the narrative beats (headline, tension, evidence charts, implication,
  actions). If persona/tone matters to the demo, [needs you] to confirm.
- **Locked chapter count (default; the user can override, and you must name the
  default you used).**
  - One chapter per qualifying measure after the yearly comparison (a measure
    that qualifies is one signal, even when it moves with another; never merge
    measures to shorten the story). Chapters = qualifying measures + 2, then
    clamped to 3 to 6. The audience does not change this number; it only changes
    density and tone. State it as "Chapters: N (qualifying measures + opening and
    closing)".
  - **Chapter titles (build only):** the opening is a question about the lead
    measure ("Is <measure> growing?"). Each signal chapter's title is one
    sentence stating its result with the number from the queried rows ("Sales
    grew 51% between 2023 and 2026."). Signal chapters run in lead-signal order,
    then by relative change, largest first. The closing is "What to review"
    (executive) or "What this means" (analyst). The story title is
    "<Datasource name exactly as listed> <lead measure> brief" for a Report brief
    (for example "Superstore Datasource Profit brief"), and the audience never changes the
    chapter order. Numbers in titles use the yearly figures once the seasonality
    check ran.
  - Plus one opening chapter that frames the question and one closing chapter
    for implications or actions.
  - **The limit of 6 holds after the build too.** Do not offer extra chapters or
    follow-up analysis the user did not ask for. If the user asks for another
    chapter, the story keeps 6: say which existing signal chapter it would replace
    (the one with the smallest yearly change) and offer that swap. Never propose a
    seventh chapter.
  - Minimum 3 chapters, maximum 6. If more than 4 signals qualify, keep the 4
    with the largest relative change and mention the rest in the closing chapter.
  - This count feeds the pinned versus numbered-chapter tie-break above (4+ beats means numbered chapters).
- **The chosen template's chapter list is a starting mechanics reference, not
  the target shape.** Let the real signal and the intended audience decide
  which acts exist, how many, and in what order. If the data only supports 3
  clean beats, ship 3 — don't stretch to fill every template chapter. If the
  story needs a chapter the template doesn't have, add one using the same D3
  patterns. If a template chapter (e.g. a facility/market rail, a segment
  quadrant) has no honest analog in the real data, drop it (this is also
  called out in step 4) rather than forcing the data to fit its shape.

## 4. Build the scrollytelling HTML — automatic

- Copy the chosen template from this skill's `assets/public/` into the scratch
  dir (`.build/scrollytelling-demo-builder/`). Never edit the vendored templates
  in `assets/` in place.
- **The template is a style/structure guideline, not a literal copy.** It came
  grounded in a different story's numbers, so it is full of magic numbers tuned
  to THAT story's scale: axis domains (e.g. a margin axis hardcoded to
  `[12,20]`), $-vs-% formatting, and quadrant/threshold cutoffs (e.g. "leaking"
  defined as a specific dollar band). None of these transfer to a new
  datasource by accident. **Never leave a hardcoded domain, threshold, or unit
  literal that was copied from the template's original story** — find every
  such constant the chapter you're adapting depends on and recompute it from
  the real rows you queried (e.g. `d3.extent`/min/max of the actual field, or a
  median/percentile split of the real values) before wiring that chapter to new
  data. If a template device has no honest analog in the new data (e.g. a
  "leak size" axis when your data's volume field is nearly uniform across
  groups), say so and either drop that chapter or pick a different real field
  for it — never force a fabricated or misleading number in just to fill the
  shape.
- Adapt to the datasource:
  - Rewrite **`const MEAS`** to your measures/dimensions (`.cap` = the exact
    datasource caption; correct unit/format/aggregation).
  - Set **`WS_NAMES`** with your feeder sheet name (e.g. `feed_data`) at the front.
  - Rewrite **`contractFromRows`** so it reshapes your feeder rows into the
    SEED-shaped arrays each draw fn expects (`colIdx(sub)` substring-matches
    captions, bare or `AVG(...)`-wrapped).
  - Set **`const SEED`** from the REAL numbers you queried, so Demo mode tells the
    true story and matches Live mode.
  - **Audit every draw function you touch for copied-over domains/thresholds**
    (chart axis ranges, color-bucket cutoffs, `$`/`%`/unit literals in labels
    and tooltips) and recompute each against the real data's actual range —
    do this chapter by chapter, not as one global find/replace, since each
    chapter tends to have its own hardcoded scale.
  - Adapt copy, chart fields, and marks; keep the animations and interactions
    (reveals, count-ups, modals, dot-nav, Demo/Live toggle, and the **Explore
    view** — see `style-guide.md`: keep the story prose unfiltered, adapt the
    Explore filter set to your datasource's dimensions, and preserve its
    live-only greying so no row-level data is ever fabricated).
- **Check `python3` is actually available before running the build script** —
  never assume it. Run `python3 --version`; if it fails (not installed, not on
  PATH), stop and [needs you]: tell the user to install Python 3 (or point you
  at the `python3` binary) before you can continue.
- Build the self-contained bundle with `assets/build_standalone.py`. Confirm
  **0 external `<script src>`** and no secrets in the output.
  - **Hosted:** use `--extension`, plus `--persona cfo` if using that template.
  - **Packaged:** use `--template <your adapted copy> --packaged --query <q.json>`,
    per step 4P.
  - Either mode: a plain build with no flags (`--template` only) renders from
    SEED in a local browser. That is your only preview for packaged mode, so
    check layout there first.
- **Give shared `<defs>` gradients/filters/patterns a single global id, never a
  per-chart duplicate** — reuse the templates' one shared `injectGlobalDefs()`
  (called once from `boot()`) for any new shared def. Duplicate def ids paint
  charts intermittently blank; see *Known failure modes §B*.

## 4P. Packaged mode: query, package, publish, verify (automatic, plus [needs you] for project and credentials)

Follow `references/packaged-extension.md`. It covers prerequisites, query format,
commands and failure modes. In order:

1. **Check setup.** Run `python3 assets/package_extension.py check`.
   - **Exit 2 or `missing`:** [needs you]. Have the user run `configure` (server,
     site content URL, PAT name), then `store-secret`, which prompts in *their*
     terminal. Never take the secret in chat.
   - **`packages: unavailable`:** [needs you]. A site admin must enable
     Settings > Packages. Offer hosted mode as the fallback.
2. **Write the live query** in the scratch dir. It is the VDS form of what
   `feed_data` would hold:
   - the day-truncated date, the story dimensions, and each measure aggregated
     as `MEAS` expects;
   - **every field aliased to its `MEAS` caption**;
   - **the exact step-2 window filter**.

   Validate it with `package_extension.py query --query <q.json>`. Check the row
   count, keys and magnitudes against your probe before building.
3. **Build** with `build_standalone.py --template <adapted.html> --packaged --query <q.json> --out <scratch>/story-pkg.html`,
   then `package_extension.py build --html ... --name "<Story Name>" --datasource "<exact DS name>" --out-dir <scratch>`.
4. **Confirm the target project with the user** ([needs you]). Then run
   `package_extension.py publish --twbx ... --project "<project>" --image <scratch>/check.png`.
   - Expect a single `sqlproxy` connection to the chosen datasource.
   - Re-publishing while iterating overwrites the same workbook and needs no
     re-confirmation.
5. **Verify.** Read `check.png`:
   - The story must render.
   - At least one headline `[data-v]` number must equal the value computed from
     the `query` rows, not the SEED value. A SEED number means the live read
     failed (see the reference's failure modes).

   Then [needs you]: the user opens the printed view URL and checks scrolling,
   the Demo/Live toggle, and the Explore filters.

## 5. Add the feed_data sheet — automatic; dashboard placement is [needs you]

- **Check for an existing `feed_data`-shaped sheet first** (`list-worksheets` /
  `get-workbook-inventory`): if this workbook already has a worksheet matching
  `WS_NAMES` (or named `/feed/i`) from a prior run on the same story, inspect
  whether it already carries the right dimensions/measures/window before
  building a new one from scratch — reuse and adjust it if so, rather than
  creating a duplicate feeder sheet.
- **Connect the datasource the story uses first.** The feeder must come from the
  datasource the user chose, in this workbook. If the open workbook is connected to
  a different one, do not swap silently and do not build on it: connect the chosen
  datasource through the workbook CLI's datasource commands, and only if those
  cannot express it, hand the user to Data > New Data Source with the exact
  project and name. Never ask the user to pick between "connect it" and "use
  another datasource" unless the chosen one cannot be reached.
- Author the **`feed_data`** feeder crosstab **per the recipe in
  `style-guide.md`** (discrete Day-Trunc date × story dimensions on rows, each
  measure aggregated as `MEAS` expects, the multi-measure Text-mark pattern),
  **filtered to the exact window chosen in step 2** — a `Day_Offset`-in-range
  filter (or equivalent date filter) if the datasource has a day-offset field.
  This filter is required, not optional: omitting it silently reverts the feeder
  to the full history, which dilutes/hides the signal even though the sheet still
  "applies cleanly." After building, sanity-check the MIN/MAX of `DAY(Date)`
  against the chosen window, and sample measure magnitudes against plausible
  real-world values, in `get-summary-data`'s output before moving on — confirm
  the real shape there, not just a clean apply receipt.
- **If Tableau rejects the sheet edits twice**, stop. The stop reply for that case
  names the half-built sheet (see SKILL.md "Clean stop"). Hand over the manual
  recipe: Order Date (discrete Day) on Rows, then the story dimensions; Marks set
  to Text with each measure as SUM on Text; the window filter from step 2.
- Leave it as a normal (non-floating) worksheet for now — do not try to place or
  float it yourself. Placement happens in the [needs you] step below.

- **Do not author the dashboard, its zones, or the sheet placement yourself.**
  Automated `apply-dashboard` and the native `tabdoc:drop-on-dashboard` corrupt
  the dashboard at the Tableau engine level for this operation (see *Known
  failure modes §A*) — this is a known limitation, not optional politeness, so
  tell the user plainly why you're handing it off. Hand the whole thing to the
  user as one [needs you] step, spelled out as literal numbered clicks regardless
  of prompting level (Minimal may compress wording, but never drop a numbered
  step here — this sequence has repeatedly gone wrong when compressed).

  **Your first message to the user must list all 5 steps below in full**, even if
  you then walk them through it one step at a time in later turns. Doing this
  step-by-step across multiple turns (waiting for confirmation after each) is fine
  and expected — but re-deriving or re-summarizing the list from memory turn-to-
  turn is not: it has already caused step 2 (Automatic sizing) to be silently
  dropped when only steps 1/3/4/5 were narrated. Before presenting each step,
  re-read this numbered list from the file rather than recalling it, and confirm
  the step number you're about to give matches this list exactly:
  1. **Add a new dashboard.** Right-click the sheet tab bar at the bottom of
     Desktop → **New Dashboard**. (If you already created the dashboard in a
     prior turn, skip to step 2 on that existing dashboard.)
  2. **Set the dashboard to Automatic sizing.** In the Dashboard pane on the
     left, under **Size**, change the dropdown from **Fixed size** to
     **Automatic** — this lets the Extension tile fill the available space
     responsively instead of clipping at a fixed canvas size.
  3. **Place `feed_data` as a floating object.**
     - In the left-hand **Sheets** list, drag **`feed_data`** onto the
       dashboard canvas.
     - By default it drops as a **tiled** object filling part of the canvas —
       that's fine, it will be moved next.
     - Click the `feed_data` object once to select it. In the **Layout** pane
       (left side, opens when an object is selected), check the **Floating**
       checkbox — if it's tiled, right-click the object on canvas → **Floating**
       first, then select it again so the Layout pane shows position/size
       fields.
     - In the Layout pane's **Position** fields, type **x = −3000** and

## Known failure modes

The rationale behind the guardrails in the steps above. Read the referenced item
when you hit the symptom — don't re-litigate the decision.

**§A — Automated dashboard placement corrupts the dashboard (step 1 checkpoint,
step 5 manual handoff).** `apply-dashboard` and the native
`tabdoc:drop-on-dashboard` are unreliable for adding the feeder + Extension and
have repeatedly corrupted the dashboard object at the Tableau engine level in
testing — not just a tool-side validation quirk. Symptoms seen:
`apply-dashboard`/`drop-on-dashboard` report `"Dashboard references sheet 'X'
which has no visual representation in the workbook"` even for a trivial one-field
worksheet on a brand-new dashboard; `get-dashboard-xml` readback shows the zone
present and looking correct while Desktop's own UI still throws the identical
error as a hard, modal dialog when the user clicks the dashboard's tab (`Error
Code: 2805CF18` seen once) — and once that happens, `delete-sheet` on the
dashboard itself starts failing with an internal error too, so even cleanup
requires the user's hand. **Do not attempt automated `apply-dashboard` calls at
all for this skill** — hand placement to the user (step 5).

**§B — Duplicate `<defs>` ids paint charts intermittently blank (step 4).** Never
give a chart's local `<defs>` gradient/filter/pattern a fixed `id` that another
chart on the page also uses. Both templates already call one shared
`injectGlobalDefs()` (invoked once from `boot()`) for the `#gg` gradient and
`#glow` filter — reuse that pattern for any new shared def instead of adding a new
per-chart local `<defs>`. `url(#id)` resolves against the whole document's id
table, not the local `<svg>`, so duplicate ids plus each chart's redraw cycle
(`selectAll("*").remove()` + re-append) could transiently leave a reference
pointing at a mid-teardown node — Chrome then paints that stroke/fill as nothing.
Symptom looked exactly like "chart renders with fully correct data/DOM but is
visually blank," intermittently, and a hard browser reload only sometimes appeared
to fix it (coincidence, not a real fix). Don't chase that symptom as a
data/caching bug — check for duplicate def ids first.

**§C — `.trex` silently overwritten with prose (step 6).** If Desktop rejects the
`.trex` with "Error parsing extension manifest: Fatal Error(1,1): invalid document
structure," don't assume the manifest logic is wrong — first check the file at the
visible path is still valid XML (`cat` it / open it). It's been overwritten with
unrelated plain text in testing (its content silently became session-notes prose,
not XML), which produces exactly this parse error. Re-copy a known-good `.trex`
(the scratch-dir copy, or `assets/example-*.trex`) to the visible path rather than
trying to hand-repair the corrupted file.
